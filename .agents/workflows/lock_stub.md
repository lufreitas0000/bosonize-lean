# /lock_stub

**Description:** Transitions a chapter from Phase A (Staging) to Phase B (Interactive Proof Search) after Human-in-the-Loop approval.

**Instructions for the Agent:**
When the user invokes `/lock_stub <Chapter Number>` (e.g., `/lock_stub 1`), execute the following steps:

1. **Acknowledge Approval:** Acknowledge that the definitions, margin constraints, and theorem signatures in `BosonizeStubs/ChNN.lean` have been mathematically validated by the human architect.
2. **Verify or Establish the Approved Baseline:** From the repository root, run `python3 scripts/guards/stub_lock.py --check --strict` if a lock already exists. Preserve a matching baseline. A failure requires investigating the exact drift; do not overwrite the baseline to make the check pass. Use `--update` only for explicitly approved initial locking or baseline changes, and review the full manifest diff because it rewrites the baseline for all staging files. Confirm that the approved chapter is actually present in the manifest. The v2 guard freezes theorem/lemma headers, full non-lemma commands, and preceding non-lemma context. Strict mode also rejects additions. Review the frozen definitions and instances along with statements; preserve `stub_locks.json` as legacy evidence and use `stub_locks.v2.json` as the active baseline. `--update` refuses changed frozen content unless `--accept-changes` is explicitly authorized and is disabled in CI. See `docs/spec/freeze_audit.md`.
3. **Transition to Phase B:** Once locked, immediately transition your operational mode to Phase B (Tactical Execution).
4. **Initiate Proof Search:** Use the user's selected lemma or an already authorized proof scope. Read the source proof sketch and all chapter-relevant `docs/proof_suggestion/` files. Critically check suggested tactics, helpers, imports, and hypotheses against the installed Lean/Mathlib before adopting them. Query `lean_goal` and follow the formalizer retrieval hierarchy; if MCP tools are unavailable, use the compiler and local sources and report that fallback. Preserve the approved definitions, instances, names, namespace, and signatures. After each proof batch, run the guard, inspect the source diff for unguarded changes, build staging, and update the companion notebook. Do not regenerate locks during proof search.
