# Phase C: Audit, promote, and freeze

Execute automatically for a fully proved chapter within an authorized A–B–C cycle, after all Phase B audit criteria pass. Honor any explicit phase-only/stop instruction. Follow [the pipeline policy](../skills/formalizer/references/pipeline.md); routine promotion does not need a new human confirmation.

1. Check the chapter against its approved definition/statement baseline. Require no `sorry`/`admit`, no compiler warnings, and only `propext`, `Classical.choice`, and `Quot.sound` in every lemma's axiom dependencies. Use freshly built declarations for the axiom audit.
2. Plan the exact source-path and import migration. If chapters and supporting appendices are promoted together, independently review required staging-to-Core import substitutions before applying them; preserve mathematical declarations and proof bodies. Rebuild and repeat axiom checks after those substitutions. Move the completed source from `BosonizeStubs/` to `Bosonize/Core/`. Preserve the Lean namespace, definitions, and statements. Add its import to `Bosonize.lean` and remove its direct staging import from `BosonizeStubs.lean`; staging already imports the Core aggregator.
3. Move the existing chapter entry in `docs/spec/stub_locks.v2.json` to its new source path, preserving every unchanged declaration/command hash. For the independently reviewed import substitutions in step 2, recompute only the affected import-command hashes and dependent context entries in the promoted modules; retain all theorem-header and other command hashes. Inspect and document the exact manifest delta. This is a scoped path/import migration, not permission to change other chapters or regenerate the entire interface baseline.
4. Record the promoted file's SHA-256 in `docs/spec/core_locks.json` without altering hashes of existing Core files. `core_lock.py` has no automatic update command: extending this manifest belongs to this validated, authorized chapter promotion. Core proof bodies must now remain unchanged along with definitions and statements.
5. Move and update the companion notebook under `docs/companion/Bosonize/Core/`. Include proof strategy, exact source, axiom output, validation evidence, and the approved baseline migration. Retain the v1 manifest as historical migration evidence.
6. Update the corresponding pedagogical chapter note in `notes/md/` and, for promoted supporting appendix work, the corresponding `notes/appendices/` section using [the pedagogical-sync skill](../skills/pedagogical-sync/SKILL.md). Keep the companion focused on the formal Lean document and this pedagogical Markdown as a complementary lecture note about the Lean file. Preserve the original reference information and explain the abstract theory together with the actual verified constructive realization in natural mathematical language. Match carriers, parameters, assumptions, scope and proof status to the final Lean source; record declaration mapping/evidence in the companion. Obtain an independent agent review of the pedagogical diff and resolve its findings. Documentation must pass this gate before Phase C is complete.
7. Run both guards, their tests, and both Lean library builds through `make ci`. Import the Core aggregator for the final axiom audit to verify the promoted chapter is accessible to downstream chapters.
8. Commit the completed proof work, pedagogical note, companion and promotion checkpoint. Verify both guards against that committed Git reference and report the commit and final working-tree status. Do not begin the next chapter unless it is included in the user's authorized scope.
