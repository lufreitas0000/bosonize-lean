# /start_chapter

**Description:** Begins chapter development with Phase A, then advances through independently reviewed Phase B/C under the automatic pipeline unless the user explicitly requests Phase A only.

**Instructions for the Agent:**
When the user invokes `/start_chapter <Chapter Number>` (e.g., `/start_chapter 1`), execute the following steps:

1. **Read Source Material and Suggestions:** Locate and read the corresponding Markdown notes in `notes/md/` (e.g., `notes/md/ch01_lattice_band_geometry.md`) and cross-reference with `notes/md/TOC.md` and chapter-relevant `notes/appendices/`. Read chapter-relevant files in `docs/stub_suggestion/` and inspect `docs/proof_suggestion/` for potential interface requirements. Reconcile applicable review corrections with current source versions; both the statements and the suggested proofs require scrutiny. Use the relevant sections of `.agents/skills/formalizer/references/proof_design.md` to assess carriers, source/target budgets, operator order, margins, and existence obligations. Report false or underspecified claims and propose repairs; do not copy incomplete definitions or change assumptions silently to make suggested proofs succeed. If the chapter already has a lock, check it and preserve its approved interface rather than redrafting it.
2. **Draft Signatures:** Create a new Lean file in `BosonizeStubs/` (e.g., `BosonizeStubs/Ch01LatticeBand.lean`). Translate the mathematical definitions and claims into Lean 4 `def`, `abbrev`, and `theorem` signatures. Ensure all `def` and `abbrev` blocks are complete, and all `theorem` or `lemma` signatures terminate with exactly `:= by sorry`.
3. **Generate Lab Notebook:** Create a mirrored Markdown documentation file at `docs/companion/BosonizeStubs/` (e.g., `docs/companion/BosonizeStubs/Ch01LatticeBand.md`). Document your design rationale, the specific Mathlib structures you chose, and how you formalized any physical margin constraints or edge cases. Identify source versions, relevant appendices/corrections, and the suggestions adopted, adapted, or rejected. Include proposed helper dependencies, useful local hypotheses, witness obligations, and unresolved mathematical issues. Distinguish an elaborated definition or witness stub from a proved result. Keep the source snapshot synchronized with approved names and statements.
4. **Independent Review and Transition:** Follow [the pipeline policy](../skills/formalizer/references/pipeline.md). Delegate mathematical/interface review to another agent, resolve deterministic findings and re-review the affected final source. Record identity, source hash, verdict and validation evidence in the notebook. After a passing review, establish the scoped committed lock with `lock_stub.md`, then proceed through Phase B and `freeze_chapter.md` automatically. Ask the user only for substantive ambiguity. Honor an explicit instruction to stop after Phase A or perform review only.
