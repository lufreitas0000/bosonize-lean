# Automatic chapter pipeline and independent review

The user adopted this repository-specific policy on 2026-10-09. A request to develop a named chapter or supporting appendix authorizes its A–B–C cycle, including independent review, troubleshooting, initial locking, justified staging-interface corrections, proof work and validated promotion. Routine phase confirmations are unnecessary. Explicit phase-only/stop instructions override the default. A workflow-update or review-only request is not itself a request to prove a chapter. Do not start other chapters or silently rewrite previously promoted Core. This policy is executed by agents during authorized work; it is not a background scheduler or a recurring automation.

## Phase A and the independent gate

1. The primary formalizer reconciles sources and constructs complete data, one-sorry theorem stubs and the exact companion notebook. Check the installed APIs, staging/Core builds, data axiom dependencies and preserved locks. Strict verification should identify the new unlocked draft before approval; do not conceal that expected state.
2. Delegate review to another agent that did not author the draft. Give it the current source, companion, source notes, relevant appendices/corrections and this skill. Require an independent assessment rather than agreement with the primary's conclusions. The reviewer should be read-only on guarded files; scratch checks belong outside guarded directories. Shared workspaces require clear edit ownership.
3. The reviewer checks source fidelity, type/carrier choices, explicit hypotheses and their necessity, nonvacuity/witnesses, operator order/signs, grading/margins, actual adjoints, compression remainders, series/exponential meaning, downstream use and feasible proof dependencies. Compilation with sorry establishes elaboration only. Report concrete findings, file/line, evidence or counterexample, severity and a pass/revise/escalate verdict.
4. The primary fixes deterministic defects without asking the user and reruns relevant checks. The reviewer reassesses the affected final draft. An unresolved mathematical objection blocks the transition even when builds pass. A missing independent reviewer is a blocked review gate, not permission to self-approve.
5. Record reviewer identity/task, reviewed source SHA-256, verdict, findings/resolution, compiler/MCP status, declaration/placeholder counts and data axiom audit in the companion. Verify that the current source hash matches the passing review. Update the roadmap and commit the reviewed interface and scoped lock baseline before proof-body edits.

## Scoped lock establishment and correction

Use `.agents/workflows/lock_stub.md` and the existing guard APIs. Initial locking may add only independently reviewed active-chapter records. A guard update can generate records for every staging file: isolate the candidate output if needed and merge only the authorized entries, then compare against the committed previous manifest. Leave all unreviewed chapters, historical manifests and Core records unchanged. Never claim the entire generated baseline is approved merely because the active chapter passed review. Unreviewed staging files can still block strict CI; identify them rather than lock them implicitly.

During Phase B, proof bodies are the normal edit boundary. If new helpers, imports, data or headers are needed, stop edits to that interface, save the exact before/after diff and justification, and obtain independent review. Adding helpers that decompose the same goal, fixing a checked API, or removing a provably redundant assumption can be routine. Do not silently strengthen hypotheses, weaken conclusions or change physical conventions to make a proof pass. Re-run elaboration/axiom checks, amend only the affected staging records, commit the revised baseline and resume with strict checks against it. Do not use a guard update to mask accidental drift. Existing Core remains immutable; a discovered upstream error needs a separately scoped resolution.

## Phase B troubleshooting and Phase C

Prove the reviewed interface in dependency order, with strict guards around proof batches and notebook evidence for remaining stubs. After three unsuccessful attempts at one unchanged goal, stop that approach and delegate a concrete troubleshooting/decomposition task: goal, relevant definitions, attempted tactics, diagnostics and constraints. This is a diagnosis/decomposition budget, not a limit of three attempts for an entire theorem. Continue on a supported different approach. A technical obstacle can be reported as incomplete/blocked without requesting unnecessary approval.

Proceed to Phase C automatically when the whole chapter has zero placeholders/warnings, freshly inspected theorem/data dependencies contain only standard axioms (or none), and source/notebook and baseline checks pass. Follow the promotion workflow, preserve old Core hashes, migrate only reviewed paths/context, run both guards and required CI/builds, audit through the Core aggregator and commit the final checkpoint. Retain phase commits and reviewer evidence. Report what was proved, validation, remaining limitations and Git status; do not imply that an agent review proves the mathematics. Sync checkpoints to the configured remote when the session authorizes that action. Automatic chapter progression does not grant unrelated external actions.

## Human involvement for ambiguity

Ask a focused question only when proceeding would require choosing between materially different interpretations, carriers, physical conventions, conclusions or scope, when reviewer/primary disagreement remains substantive, or when the intended claim is false and its replacement is not determined by the accepted sources. Provide exact alternatives and evidence, including downstream impact. Continue independent work while that decision is pending; elapsed time is not approval. Never promote the affected unresolved work.

Do not ask for confirmation merely because a phase ends, a lock must be created, a compiler issue has an unambiguous repair, a provably redundant assumption can be removed, or a scoped helper decomposition needs adding. Record/re-review those actions instead. Report unavailable tools and incomplete work candidly. The user remains free to inspect evidence, narrow scope or stop at any time.
