# Automatic chapter pipeline and independent review

The user adopted this repository-specific policy on 2026-10-09. A request to develop a named chapter or supporting appendix authorizes its A–B–C cycle, including independent review, troubleshooting, initial locking, justified staging-interface corrections, proof work and validated promotion. Routine phase confirmations are unnecessary. Explicit phase-only/stop instructions override the default. A workflow-update or review-only request is not itself a request to prove a chapter. Do not start other chapters or silently rewrite previously promoted Core. This policy is executed by agents during authorized work; it is not a background scheduler or a recurring automation.

## Usage gate before automatic progression

Apply [Usage allowance and resumable checkpoints](usage_budget.md) before starting a chapter, changing phase or dispatching a parallel proof group, and approximately every 5–10 minutes during sustained work. Below 10% remaining in the five-hour window or 5% in the weekly window, save the current phase accurately and yield with a recommendation to pause. Automatic A–B–C progression resumes only under the reference's resumption policy; low allowance does not authorize incomplete promotion, weakened proofs or altered locks.

## Phase A and the independent gate

1. **External drafting:** Prepare a bounded packet for Jules, eligible API generation, or the human browser route. Require complete definitions, one-sorry contracts, and the exact companion. Desktop/Antigravity subagents are not a default fallback.
2. **Orchestrator Review & Proofreading:** The orchestrator (or an independent external reviewer) proof-reads and strictly verifies the drafted file against the natural language notes. Check source fidelity, carrier types, explicit hypotheses and their necessity, nonvacuity/witnesses, operator order/signs, grading/margins, actual adjoints, compression remainders, series/exponential meaning, downstream use and feasible proof dependencies. Compilation with sorry establishes elaboration only. Report concrete findings, file/line, evidence or counterexample, severity and a pass/revise/escalate verdict.
3. **Deterministic Defect Resolution:** The primary fixes deterministic defects without asking the user and reruns relevant checks. An unresolved mathematical objection blocks the transition even when builds pass.
4. **Lock & Baseline Commitment:** Record reviewed source SHA-256, declaration/placeholder counts, and data axiom audit in the companion. Freeze the reviewed interface in `docs/spec/stub_locks.v2.json`, commit the baseline atomically, and advance automatically to Phase B.

## Scoped lock establishment and correction

Use `.agents/workflows/lock_stub.md` and the existing guard APIs. Initial locking may add only independently reviewed active-chapter records. A guard update can generate records for every staging file: isolate the candidate output if needed and merge only the authorized entries, then compare against the committed previous manifest. Leave all unreviewed chapters, historical manifests and Core records unchanged. Never claim the entire generated baseline is approved merely because the active chapter passed review. Unreviewed staging files can still block strict CI; identify them rather than lock them implicitly.

During Phase B, proof bodies are the normal edit boundary. If new helpers, imports, data or headers are needed, stop edits to that interface, save the exact before/after diff and justification, and obtain independent review. Adding helpers that decompose the same goal, fixing a checked API, or removing a provably redundant assumption can be routine. Do not silently strengthen hypotheses, weaken conclusions or change physical conventions to make a proof pass. Re-run elaboration/axiom checks, amend only the affected staging records, commit the revised baseline and resume with strict checks against it. Do not use a guard update to mask accidental drift. Existing Core remains immutable; a discovered upstream error needs a separately scoped resolution.

## Phase B troubleshooting and Phase C

1. **External proof batches:** Partition approved statements into dependency-aware tasks with one active owner per output. Accept browser/API/Jules candidates only through the same compiler, statement and axiom checks.
2. **Bounded troubleshooting:** After three failed attempts at an unchanged goal, preserve full diagnostics and request a targeted independent external diagnosis within the task budget, or checkpoint/defer. No silent desktop/paid fallback.
3. **Integration & Completion Decision:** The orchestrator collects, verifies, and integrates the sectional proofs into the staging file, runs strict stub-lock checks (`stub_lock.py --check --strict`), builds with `lake build`, audits axioms (`#print axioms`), ensures zero `sorry` placeholders and zero warnings remain, and decides whether to conclude Phase B.
4. **Phase C Promotion & Pedagogical Sync:** Proceed to Phase C automatically when Phase B criteria pass. Follow the promotion workflow, preserve Core hashes, and assign an external worker following the [pedagogical-sync skill](../../pedagogical-sync/SKILL.md)  to update the corresponding chapter/appendix note in natural mathematical language reflecting the verified Lean realization. The orchestrator reviews the pedagogical diff, verifies that `make lock-check` and CI guards pass, commits atomically, and updates the Kanban roadmap. Retain phase commits and reviewer evidence. Report what was proved, validation, remaining limitations and Git status. Automatic chapter progression does not grant unrelated external actions.

## Human involvement for ambiguity

Ask a focused question only when proceeding would require choosing between materially different interpretations, carriers, physical conventions, conclusions or scope, when reviewer/primary disagreement remains substantive, or when the intended claim is false and its replacement is not determined by the accepted sources. Provide exact alternatives and evidence, including downstream impact. Continue independent work while that decision is pending; elapsed time is not approval. Never promote the affected unresolved work.

Do not ask for confirmation merely because a phase ends, a lock must be created, a compiler issue has an unambiguous repair, a provably redundant assumption can be removed, or a scoped helper decomposition needs adding. Record/re-review those actions instead. Report unavailable tools and incomplete work candidly. The user remains free to inspect evidence, narrow scope or stop at any time.
